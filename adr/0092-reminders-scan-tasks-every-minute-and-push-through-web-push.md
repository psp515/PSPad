# ADR-0092: Reminders scan tasks every minute and push through Web Push, keys in Mongo

> Status: Active

## Context

A task app on a phone has to notify while it is closed. A closed PWA can't
wake itself: only a browser vendor's push service can, and it accepts
messages from a server that identifies itself with a VAPID key pair
(RFC 8030, 8291, 8292). PSPad is self-hosted, usually one `api` container,
and adds no infrastructure lightly (AD-1, no messaging bus). A reminder's
moment depends on the task's due date or repeat, its completions, its list's
members and each member's stored time zone, all of which change through
ordinary commands, offline and last-write-wins (AD-5).

## Decision

We will add a server-only `PSPad.Module.Reminders`, referencing `Tasks` and
`Identity`. The reminder setting is a field on `TodoTask`, set by a shared
command. A hosted service in the `api` container scans the tasks that have a
reminder every minute and computes their moments fresh with a pure domain
rule; it stores no fire times. Each send is claimed by inserting a
`(task, occurrence, user, moment)` record under a unique index, which is also the
duplicate guard across restarts and instances. The VAPID key pair is
generated by the API on first start and stored in MongoDB.

## Considered alternatives

- **A stored next-fire-time per task and user, kept by event handlers.**
  Cheap ticks, but every change that moves a moment (due date, repeat,
  completion, membership, time zone) needs a handler, and a missed one is a
  silent wrong reminder. The scale it buys is far beyond a self-hosted
  install.
- **Client-side scheduling.** The Notification Triggers API was abandoned; a
  closed PWA can't run code on a timer.
- **A separate scheduler container or a job library.** One more thing to run
  and configure for a one-query-a-minute loop.
- **VAPID keys from environment variables.** Survives a database wipe, but
  adds a setup step and a private key in `.env`; a wiped database loses the
  tasks the reminders are for anyway.
- **A lease so one instance schedules.** The unique claim already prevents
  double sends.

## Consequences

- Edits, completions, membership and time-zone changes affect reminders on
  the next tick without extra code.
- A tick costs one indexed query plus a computation per task with a reminder
  and recipient; fine for thousands, wrong for millions.
- Restoring a MongoDB backup keeps devices subscribed; losing the database or
  the `vapidkeys` document means every device turns notifications on again.
- Delivery is best effort: the push service may delay or drop a message, and
  a moment missed by more than an hour of downtime is skipped.
- The claim names the moment, so a reminder moved to a later time after it
  fired fires again, and one moved back to a moment that fired does not.
- The claim is written before the send, so a crash between them can lose that
  one reminder (at most once) rather than repeat it.
- `api` needs outbound HTTPS to the browser vendors' push services.
- The new module edges `Reminders`→`Tasks` and `Reminders`→`Identity` join
  `Statistics`→`Tasks` and `Sharing`→`Tasks`.
