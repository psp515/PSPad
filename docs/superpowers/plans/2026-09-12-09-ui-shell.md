# UI Shell Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the client's placeholder chrome with a responsive shell — light and dark themes, breakpoint-aware navigation, and a split floating action button every screen can drive.

**Architecture:** App sections and user areas live on separate surfaces at every width: a sidebar and area chips at `md`+, a bottom bar and an area sheet below that. Both branches are always in the DOM, separated by MudBlazor's CSS display utilities, so nothing flashes on load. Pages declare their floating-button actions through a scoped `FabContext` service rather than the layout sniffing routes.

**Tech Stack:** .NET 10 Blazor WebAssembly, MudBlazor 9.9.0, bUnit, xUnit v3.

**Spec:** `docs/superpowers/specs/2026-09-12-ui-ux-redesign-design.md`

## Global Constraints

- Target framework `net10.0`, `Nullable` enable, `TreatWarningsAsErrors` true. A warning fails the build.
- No comments in code or markup, except one line for a genuinely counter-intuitive constraint saying *why*, never *what*.
- Every test class carries `[UnitTest]` from `PSPad.TestInfrastructure`. This plan adds no integration tests.
- `PSPad.App` references `PSPad.Module.Tasks`, `PSPad.Abstractions` and `PSPad.Contracts` only. Never `PSPad.Infrastructure`, never `PSPad.Api`.
- This plan touches presentation only. No command, event, aggregate or sync change. If a task seems to need one, stop and ask.
- One type per file; the filename matches the type.
- bUnit conventions established by plan 07, which this repo's existing tests follow: derive from `Bunit.TestContext`, call `Render<T>()` and never the obsolete `RenderComponent<T>()`, and set `JSInterop.Mode = Bunit.JSRuntimeMode.Loose` in every arrange block because MudBlazor inputs call `mudKeyInterceptor.connect` through JS.
- Run tests with `dotnet test --project <path> --filter Category=Unit`. A bare positional path fails on this toolchain — always `--project`.
- Code, comments, commits and docs in English.

`src/PSPad.App/Theme/ThemePreference.cs`:

```csharp
using Microsoft.JSInterop;

namespace PSPad.App.Theme;

public sealed class ThemePreference(IJSRuntime js)
{
    const string StorageKey = "pspad.theme";

    bool _systemPrefersDark;

    public ThemeMode Mode { get; private set; } = ThemeMode.System;

    public bool IsDark => Mode switch
    {
        ThemeMode.Light => false,
        ThemeMode.Dark => true,
        _ => _systemPrefersDark
    };

    public event Action? Changed;

    public async Task InitialiseAsync(bool systemPrefersDark)
    {
        _systemPrefersDark = systemPrefersDark;

        var stored = await ReadAsync();
        Mode = Enum.TryParse<ThemeMode>(stored, out var parsed) ? parsed : ThemeMode.System;

        Changed?.Invoke();
    }

    public async Task CycleAsync()
    {
        Mode = Mode switch
        {
            ThemeMode.System => ThemeMode.Light,
            ThemeMode.Light => ThemeMode.Dark,
            _ => ThemeMode.System
        };

        await js.InvokeAsync<string>("localStorage.setItem", StorageKey, Mode.ToString());
        Changed?.Invoke();
    }

    async Task<string?> ReadAsync()
    {
        try
        {
            return await js.InvokeAsync<string?>("localStorage.getItem", StorageKey);
        }
        catch (JSException)
        {
            return null;
        }
    }
}
```

Storage access is wrapped because a browser with site data blocked throws rather than returning null, and a theme preference is never worth failing startup over.

    protected override async Task OnAfterRenderAsync(bool firstRender)
    {
        if (!firstRender || _themeProvider is null || _themeReady)
        {
            return;

        _themeReady = true;
        var systemPrefersDark = await _themeProvider.GetSystemDarkModeAsync();
        await Preference.InitialiseAsync(systemPrefersDark);

        StateHasChanged();

public sealed class FabContext

### Task 8: Record the decision

**Files:**

**Interfaces:**

AGENTS.md §11 requires an ADR in the same piece of work as the decision. Two decisions here are the kind someone would otherwise re-open: that sections and areas never share a navigation surface, and that theme is per-device while time zone is per-user.

- [ ] **Step 1: Write the ADR**

Copy `docs/arch/adr/template.md` to `docs/arch/adr/0013-responsive-shell-and-per-device-theme.md` and fill it out, matching the structure of the existing records. Status `Active`, date 2026-09-12, tags `ui, offline, identity`.

Context: the client had one hardcoded-open drawer at every width and no theme. Areas are unbounded user data while sections are a fixed set of five, and a single navigation surface cannot carry both without capping how many areas a user may have.

Decision: sections and areas occupy separate surfaces at every width — sidebar plus chips at `md`+, bottom bar plus sheet below it — and the theme preference lives in `localStorage` rather than on the `User` aggregate.

Alternatives weighed: areas as bottom-bar tabs, rejected because it displaces Today and Inbox, which AGENTS.md §1 names as the product's purpose, and collapses past four areas. Theme on `User` alongside the time zone, rejected because a time zone is a property of the person and must agree across devices for the Today rule to be correct, whereas theme is a property of the device and its ambient light.

Consequences: the two navigation trees are maintained separately and both render into the DOM at all times, hidden by CSS. Theme does not follow a user to a new device, and clearing site data resets it to System. No command, event or aggregate changes, so AD-3 and AD-4 are untouched.
