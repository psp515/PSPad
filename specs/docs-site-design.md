# Documentation site — Design

**Adds:** a public documentation site under `docs/`, a brand mark under
`brand/`, and the consolidation of the two compose files into one self-host
stack. Nothing above the presentation layer moves: no command, event,
aggregate, module reference or test in `src/` or `test/` changes behaviour.

## Problem

PSPad is a self-hosted application with nothing that explains how to host it.
`README.md` is written for a contributor with the .NET SDK on their machine —
it documents the development stack, the test categories and the container
layout, and says of production only that `compose.prod.yaml` "serves plain
HTTP and expects a reverse proxy in front of it". A person who wants to run
PSPad on their own hardware has to read two compose files, an nginx config, a
Mongo entrypoint script and a Keycloak realm export to discover what the stack
needs.

Two things make that worse than a missing page. `docker/compose.prod.yaml`
carries a connection string with `replicaSet=rs0` while the healthcheck
initiates the set with member host `localhost:27017`, so a driver that
performs replica-set discovery from the `api` container resolves the one
member to itself and never connects — the production stack as committed does
not start. And `docker/mongo-keyfile` is tracked, so every self-hoster would
authenticate their replica set with a secret published in a public repository.

There is also no product surface. The repository states the vision in
`AGENTS.md`, which is a working agreement for agents, not something to show a
person deciding whether to run this. The application has no mark of its own:
`manifest.webmanifest` still says `"name": "PSPad.App"` with
`"theme_color": "#03173d"`, a navy from before the sage palette.

## Goals

A landing page that makes the case for the application. A features page that
states what it actually does, and what it does not yet. An install page that
walks a self-hoster from a clone to a signed-in session, with every variable
and secret named. One compose file that works. One icon, used everywhere.

Out of scope: any change to `PSPad.Module.Tasks`, the command pipeline, sync,
or the HTTP surface. AD-1 … AD-9 are untouched and AGENTS.md §5 does not
change.

## Decisions

### D1 — Plain Astro, three pages, no documentation theme

`docs/` is an Astro project with hand-built pages: `/`, `/install`,
`/features`. Starlight was weighed and rejected. Its value is sidebar
navigation, built-in search and versioning across many pages; three pages need
none of that, and its splash template would fight the landing page, which is
the part that has to persuade rather than inform.

No CSS framework. Three pages do not earn Tailwind's build step or a component
library's weight.

### D2 — Published to GitHub Pages by its own workflow

`.github/workflows/docs.yml`, separate from `ci.yml`. `ci.yml` builds and
tests .NET and knows nothing about Node; merging the two would run a dotnet
restore for a prose change and an npm install for a domain change.

- `pull_request` — install, build. No deploy.
- `push` to `main`, paths `docs/**`, `brand/**`, `docker/**` and the workflow
  itself — build, then `actions/deploy-pages`.
- `workflow_dispatch` — manual republish.

Node 22, `npm ci`, `working-directory: docs`,
`permissions: { contents: read, pages: write, id-token: write }`,
`concurrency: { group: pages }`.

The site is served at `https://psp515.com/pspad` through a Cloudflare
Worker that proxies to GitHub Pages, so `astro.config.mjs` sets
`site: 'https://psp515.com'` and `base: '/pspad'`. Every internal link and
asset resolves through
`import.meta.env.BASE_URL` — a hard-coded `/install` works in `astro dev` and
404s in production, which is the one mistake this configuration invites.

`sharp` never runs in CI. Icon PNGs are generated by hand and committed (D7).

### D3 — Install content is read from the repository at build time

The install page does not retype the stack. Its frontmatter reads
`docker/compose.yaml` and `docker/.env.example` from disk during the build:

- The compose block on the page is the file, byte for byte.
- The environment table is parsed from `.env.example`. Each row takes its name
  and default from the assignment, and its description from the `#` comment
  line directly above it.

Documenting a new variable therefore means writing its comment in
`.env.example`, one place, and the page follows. The parser lives in
`docs/src/lib/repo.ts`.

**Amended: no test suite.** This design originally called for `vitest` unit
tests on the parser. Removed — a three-page marketing site doesn't carry the
same cost of a wrong parse as the application does, and the drift guard below
(a moved or renamed file fails the build outright) catches the failure mode
that actually matters. `docs.yml` no longer runs `npm test`.

This also buys a drift guard for free: because the page reads those two paths,
a pull request that moves or renames them fails the docs build.

The prose around the generated blocks is hand-written. D10 keeps it honest.

### D4 — One self-host compose stack, driven by `.env`

`docker/compose.prod.yaml` is deleted. `docker/compose.yaml` becomes the single
stack, and it is the self-hosting stack — the same file a contributor runs
locally, with `.env` defaults that work on `localhost` out of the box.

Services: `api` (`5000:8080`), `app` (`5001:8080`), `mongo`, `keycloak`
(`8080:8080`). Mongo publishes no port; it is reachable only on the `pspad`
network.

Every value comes from `${VAR}`, loaded from `docker/.env`, which Compose
picks up automatically from the compose file's directory. `.gitignore`'s
existing `*.env` already covers it. `docker/.env.example` stays tracked and is
the template.

`MONGO_CONNECTION` is dropped from `.env`. Compose composes the string from
`${MONGO_PASSWORD}` and `${MONGO_DATABASE}`, so the password is written once
instead of twice in two formats that can disagree. A self-hoster pointing at
an external MongoDB edits the compose file; that is a rarer case than typing
one password.

The string uses `directConnection=true`, not `replicaSet=rs0`. The replica set
is initiated with member host `localhost:27017`, so replica-set discovery from
another container cannot work; a direct connection to a single-node set still
satisfies the transaction requirement that made the replica set mandatory
(AD-9, ADR-0009). This fixes the broken production stack described under
Problem.

### D5 — The replica-set keyfile is generated at first run

`docker/mongo-entrypoint.sh` writes a keyfile into a named `mongo-keyfile`
volume when one is absent:

```sh
if [ ! -f /keyfile/mongo-keyfile ]; then
  openssl rand -base64 756 > /keyfile/mongo-keyfile
fi
chmod 400 /keyfile/mongo-keyfile
chown mongodb:mongodb /keyfile/mongo-keyfile
exec docker-entrypoint.sh mongod --replSet rs0 --bind_ip_all --keyFile /keyfile/mongo-keyfile
```

`docker/mongo-keyfile` is removed from the index (`git rm --cached`) and added
to `.gitignore`. Each installation then authenticates with a secret only it
holds, and the install page has no "first, replace this file" step to forget.

The committed key stays in git history and cannot be unpublished. The install
page says so in one line. Exploiting it requires network access to a Mongo
that no longer publishes a port.

Losing the `mongo-keyfile` volume while keeping `mongo-data` leaves an
unreadable replica set. Backups cover both volumes, and the install page says
which.

### D6 — Keycloak persists on a volume, in development mode, knowingly

`keycloak` keeps `start-dev --import-realm` and mounts a volume at
`/opt/keycloak/data`, so its H2 database and the imported realm survive
`docker compose down` and restarts.

The alternative — a `postgres` service, `KC_DB=postgres` and
`start --optimized` — is what Keycloak supports for real use, and it was
rejected for this stack: it adds a SQL container and a second database to a
deployment whose whole store is otherwise one MongoDB, for a single-user GTD
application.

The cost is real and is documented rather than hidden: dev-mode H2 is not
supported by Keycloak for production, and major-version upgrades of the
Keycloak image are not guaranteed to migrate cleanly. The install page states
this next to the backup instructions, and points at exporting the realm before
an image bump.

`KC_BOOTSTRAP_ADMIN_USERNAME` / `KC_BOOTSTRAP_ADMIN_PASSWORD` and the realm
import both apply on first start only; the install page says so, because a
self-hoster who changes the bootstrap password in `.env` afterwards and sees
no effect will otherwise assume the stack is broken.

### D7 — One icon master, rasterized into the application

`brand/icon.svg` is the single master: a sage rounded tile, a white sheet with
a folded corner, a sage check. It reads as a notepad whose contents get done,
and it survives 32 px and monochrome, which the two rejected concepts (a list
with a lit top row; a recurrence ring with a check) respectively failed on
distinctiveness and on legibility.

`docs/scripts/render-icons.mjs` uses `sharp` to write:

- `src/PSPad.App/wwwroot/favicon.png`, `icon-192.png`, `icon-512.png` —
  existing filenames, replaced.
- `docs/public/icon-512.png`, `docs/public/og.png`, `docs/public/favicon.svg`.

Run by hand via `npm run icons`, output committed. CI does not regenerate: a
rasterizer in the deploy path produces binary churn on every build for assets
that change once a year.

`src/PSPad.App/wwwroot/manifest.webmanifest` is corrected in the same work —
`"name": "PSPad"`, `"short_name": "PSPad"`, `"theme_color": "#4E7A5E"`,
`"background_color": "#F7F8F5"`.

### D8 — The sage palette, a light/dark toggle

`docs/src/styles/theme.css` declares the D12 palette from
`ui-redesign-2-design.md` as custom properties. The site and the application
look like one product. System font stack.

**Amended: a manual theme toggle, and the JavaScript that costs.** This
design originally shipped zero client JavaScript, switching palette purely by
`prefers-color-scheme`. A toggle button in the header now lets a visitor
override that — same System/Light/Dark idea the application's own account
menu offers (D12/D13 of `ui-redesign-2-design.md`), reachable here without
signing in to anything. The choice is written to `localStorage` under
`pspad-theme` and applied via a `data-theme` attribute on `<html>`.

Two small inline scripts carry this, both in `Page.astro`: one in `<head>`,
blocking, applying a stored preference before first paint (skipping it means
a flash of the wrong theme); one at the end of `<body>` wiring the toggle
button's click handler. Nothing else on the site uses JavaScript, and D2's
build still runs no Node test step against it — it's small enough to read at
a glance in the one file that has it.

### D9 — No screenshots until the client redesign lands

The client is mid-redesign: `ui-redesign-2-design.md`'s plans 10 and 11 are
unbuilt, so a screenshot taken now is wrong within a week. The landing hero
carries the icon and a hand-built CSS mock of a Today row instead. Real
screenshots are a follow-up once plan 11 lands.

### D10 — Docs ship with the change

A new rule in AGENTS.md §11:

> **Docs ship with the change.** A change to what a self-hoster runs (compose
> services, environment variables, secrets, ports) updates
> `docs/src/pages/install.astro`; a change to what the application does (a new
> screen, a new capability, scope moving from *later* to *now*) updates
> `features.astro` and the landing page. Same piece of work, never a
> follow-up. The compose block and the environment table are read from
> `docker/compose.yaml` and `docker/.env.example` at build time and need no
> hand edit — but a new variable needs its `#` description comment in
> `.env.example`, and the prose around them is hand-written.

D3 mechanises the part that can be mechanised. This rule covers the part that
cannot.

## Structure

### Files

```
brand/
  icon.svg                     master mark, single source

docs/
  package.json                 astro 5; sharp as a devDependency
  astro.config.mjs             site + base '/PSPad'
  tsconfig.json
  scripts/render-icons.mjs     sharp: brand/icon.svg to PNGs
  src/
    layouts/Page.astro         head, skip link, nav, footer
    components/
      Hero.astro
      FeatureCard.astro
      EnvTable.astro           renders parseEnvExample() output
      Step.astro               numbered install step
      Callout.astro            note / warning
      Mark.astro               inline SVG icon
    lib/repo.ts                readRepoFile(), parseEnvExample()
    pages/index.astro
    pages/install.astro
    pages/features.astro
    styles/theme.css           D12 palette, light + dark
  public/                      generated icons, og.png

.github/workflows/docs.yml
```

`docs/` holds no `.csproj` and is not added to `PSPad.slnx`. `.gitignore`
gains `docs/node_modules/`, `docs/dist/`, `docs/.astro/` and
`docker/mongo-keyfile`.

### Environment variables after consolidation

`docker/.env.example`, each entry preceded by the `#` comment that becomes its
description on the install page:

| Variable | Purpose |
|----------|---------|
| `MONGO_PASSWORD` | Password for the `pspad` MongoDB root user. Compose builds the connection string from it. |
| `MONGO_DATABASE` | Database name. |
| `KEYCLOAK_AUTHORITY` | Realm URL as the **browser** reaches it. The WASM client redirects here. |
| `KEYCLOAK_AUDIENCE` | Audience the API validates on incoming tokens. `pspad-api`. |
| `KEYCLOAK_CLIENT_ID` | Public client the browser authenticates as. `pspad-app`. |
| `KEYCLOAK_ADMIN_USER` | Bootstrap admin, first start only. |
| `KEYCLOAK_ADMIN_PASSWORD` | Bootstrap admin password, first start only. |
| `KEYCLOAK_HOSTNAME` | Public URL Keycloak issues its own links against (`KC_HOSTNAME`). |
| `API_BASE_ADDRESS` | API URL as the browser reaches it. Substituted into the client's `appsettings.json` at container start. |
| `APP_BASE_ADDRESS` | Client URL. Drives the OIDC redirect URIs and the API's allowed CORS origin. |

Every URL here is a browser-side URL. The client is WebAssembly: it calls the
API and Keycloak from the user's browser, never from inside the compose
network. A value that resolves only between containers produces a stack that
starts cleanly and cannot sign anyone in, which is the failure mode the
install page is written to prevent.

### Page content

**`/`** — mark and wordmark; one-line claim (a self-hosted GTD notepad that
works offline, on your own hardware); Install and GitHub buttons; the problem
it solves (one Today screen across every area, one Inbox); four proof points
(offline PWA with an outbox that syncs on reconnect; recurrence that never
goes overdue; action history taken from the event log, not an audit table;
multi-user through Keycloak); a Capture, Organize, Today strip; a closing
install call to action.

**`/features`** — cards for Today, Inbox and capture, Areas and lists, Tasks
and steps, Recurrence, Goals, Action history, Offline, Identity. Each states
the actual rule rather than a slogan — Today reads *due today or earlier, or
the next unchecked step is, computed in the time zone stored on your user*.
Then a **Planned** section from AGENTS.md §2 and §9 — habits, annual plans,
analytics and reminders, GitHub issues, cloud storage, the 3D-print domain,
checklists — marked plainly as not built. This is where the roadmap lives
instead of a fourth page.

**`/install`** — prerequisites (Docker with Compose v2, a reverse proxy for
TLS); clone; `cp docker/.env.example docker/.env`; the generated variable
table; `docker compose -f docker/compose.yaml up -d`; waiting for the Mongo
healthcheck; creating the first user in the Keycloak admin console; signing in
at `APP_BASE_ADDRESS`. Then reverse proxy and TLS; backups (`mongo-data`,
`mongo-keyfile`, `keycloak-data`, and a `mongodump` one-liner); upgrades; and
the two caveats stated plainly — Keycloak's dev-mode H2 (D6) and the keyfile
in git history (D5).

### Records

- **ADR-0015** — one self-host compose stack; secrets from `.env`; the keyfile
  generated at first run; Keycloak persisted in development mode. Supersedes
  nothing; records a decision that had never been written down.
- **ADR-0016** — the documentation site: Astro, GitHub Pages, repository files
  imported at build time.
- `adr/README.md` index gains both rows.
- AGENTS.md: §6 repo layout gains `docs/` and `brand/`; §11 gains the D10
  rule. §5 is untouched.
- `README.md`: links the published site, drops the `compose.prod.yaml`
  paragraph, points self-hosters at `/install` rather than restating it.

### Plans

**Plan 12 — stack and mark.** The compose consolidation (D4), the keyfile
change (D5), the Keycloak volume (D6), `brand/icon.svg` and the icon script
(D7), the manifest correction, ADR-0015, and the AGENTS.md edits. Ends with
`docker compose -f docker/compose.yaml up -d` bringing up a stack that a
browser can sign in to from a clean clone.

**Plan 13 — the site.** The Astro project, the palette, the three pages, the
build-time import and its tests (D1, D2, D3, D8, D9), `docs.yml`, ADR-0016,
the README edit. Ends with the site published at
`https://psp515.com/pspad`.

Stack first: the install page is generated from the compose file, so the
compose file has to be the final one before the page is written against it.

## Testing

No unit test suite — removed after the first pass; a three-page marketing
site doesn't carry the parser-correctness risk that justified it, and the
guard below catches the failure mode that actually matters.

The pull-request job in `docs.yml` is the guard: the pages import
`docker/compose.yaml` and `docker/.env.example`, so a change that moves,
renames or deletes either fails the build.

Verified by hand, not asserted: how the pages look at phone and desktop
widths, both colour schemes, and that the deployed site's links resolve under
the `/PSPad` base. Pinning layout or palette values in tests only makes
changing them expensive — the same reasoning `ui-redesign-2-design.md` applies
to the client.

The stack itself is verified by hand once per plan 12: a clean clone, `cp`,
`up -d`, create a user, sign in, create a task, restart the stack, confirm the
task and the user both survive.

## Out of scope

Architecture and development pages — `adr/`, `specs/` and `README.md` already
serve the reader who wants them, and duplicating the ADR index onto a web page
guarantees the two disagree. Documentation search, versioning, translations.
A `docs` service in the compose stack: the install page is read before a stack
exists. A custom domain. Screenshots (D9). Any change to application
behaviour.
